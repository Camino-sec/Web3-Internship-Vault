## 一、为什么需要 Agent Profile？

想象一下：你要在网上请一个兼职帮你做调研。

- 你怎么知道他能做什么？→ **简历（Capability）**
- 你怎么联系到他？→ **联系方式（How to Call）**
- 你怎么给他发工资？→ **收费方式（Pricing）**
- 你怎么知道他不是骗子？→ **信誉验证（Verification）**
- 他搞砸了怎么办？→ **失败处理（Error Recovery）**

**Agent Profile 就是 Agent 的"完整简历 + 使用说明书"**——让其他 Agent、用户、平台都能快速理解它、信任它、跟它合作。

## 二、场景选择：「AI 学习助手 Agent」

### 🎯 为什么选这个？

你每天都在用的学习助手（比如 Hermes Agent）就是一个完美的例子：
- 它有明确的身份（学习助手）
- 它有能力边界（能查资料、写笔记，但不能替你考试）
- 它需要跟其他工具协作（GitHub、Obsidian、浏览器）
- 它会失败（网络断了、API 超时、理解错了你的意思）

用你**亲身经历过的东西**做分析，比抽象概念好理解 100 倍。

## 三、Agent Profile 草图（7 个维度）

### 1️⃣ 它是谁 — Identity（身份）

```
┌─────────────────────────────────────────────────┐
│  Agent Name:     学习助手 Agent                    │
│  Agent ID:       did:agent:hermes:learning-v1     │
│  Version:        1.0.0                            │
│  Owner:          Luvia（个人部署）                   │
│  Maintainer:     Hermes Agent 开源社区              │
│  Deployed on:    本地 macOS + Cloud LLM API        │
│  Created:        2026-05-10                        │
└─────────────────────────────────────────────────┘
```

**生活类比**：
- Agent Name = 你的名字
- Agent ID = 你的身份证号（全球唯一，不会搞混）
- Version = 你的"版本"——今天学了新东西的你，就是"v1.0.1"的你
- Owner = 谁"雇佣"了这个 Agent
- Maintainer = 谁负责给它"升级维护"

**为什么需要链上身份？**
- 现在的 AI Agent 没有"身份证"——你不知道一个 Agent 是谁做的、靠不靠谱
- 如果 Agent 有了链上身份（类似 ERC-8004），你就能查到它的"工作履历"

### 2️⃣ 由谁维护 — Ownership & Maintenance（所有权与维护）

```
维护模式:
  ├── 代码维护:   开源社区（GitHub PR 协作）
  ├── 运行维护:   Luvia（自己负责启动、配置）
  ├── API 费用:   Luvia 自己承担（LLM API 按 token 计费）
  └── 数据隐私:   所有对话数据存在本地，不上传

维护责任分工:
  ┌──────────────┬────────────────────────────┐
  │ 谁            │ 负责什么                    │
  ├──────────────┼────────────────────────────┤
  │ 开源社区      │ 修 bug、加功能、安全更新     │
  │ Luvia        │ 日常使用、反馈问题           │
  │ LLM 提供商   │ 模型更新、API 稳定性         │
  └──────────────┴────────────────────────────┘
```

**生活类比**：
- 就像你买了一辆车🚗——厂家负责设计和召回维修（开源社区），你负责加油和保养（API 费用、配置），加油站负责油的质量（LLM 提供商）

---

### 3️⃣ 能做什么 — Capability（能力清单）

```
✅ 核心能力（Core Capabilities）:
  ├── 📖 知识检索      → 搜索网页、读取文件、查资料
  ├── ✍️ 内容生成      → 写笔记、总结、翻译、改写
  ├── 🧮 逻辑推理      → 分析问题、对比方案、拆解流程
  ├── 🛠️ 工具调用      → 运行命令、操作文件、调 API
  └── 💬 对话交互      → 用中文/英文自然语言交流

⚠️ 有限能力（Limited Capabilities）:
  ├── 🖼️ 图片理解      → 能看图，但不能生成图片
  ├── 🔊 语音合成      → 能转语音，但不能实时通话
  └── 📊 数据分析      → 能写代码分析，但需要运行环境

❌ 无能力（Out of Scope）:
  ├── 🚫 不能替你做决定    → 只能给建议，最终决策是你的
  ├── 🚫 不能访问你的钱包  → 不能帮你转账、签名（安全红线）
  ├── 🚫 不能保证 100% 正确 → AI 会犯错，输出需要人工验证
  └── 🚫 不能记住所有历史   → 有上下文窗口限制，太早的对话会"遗忘"
```

**生活类比**：
- 核心能力 = 你的专业技能（比如你会做 PPT、写报告）
- 有限能力 = 你勉强能做的事（比如你会做饭，但只能做简单的）
- 无能力 = 你绝对不会做的事（比如你不会做手术）

**为什么要写清楚"不能做什么"？**
- 这就像药物说明书上的"副作用"——不写清楚，用户会误用，出了问题就麻烦了

### 4️⃣ 输入输出 — Interface（接口定义）

```
📥 输入（用户给 Agent 什么）:
  ├── 文本消息     "帮我总结今天的讲座笔记"
  ├── 文件附件     录音文件、PDF、图片
  ├── URL 链接     网页、Gemini 对话链接
  └── 指令         "发到小红书"、"推送到 GitHub"

📤 输出（Agent 给用户什么）:
  ├── 文本回复     分析结果、建议、解释
  ├── 文件产物     Markdown 笔记、代码文件、报告
  ├── 语音气泡     TTS 语音消息
  ├── 平台操作     发消息到 Telegram、推代码到 GitHub
  └── 状态通知     任务完成、错误警告

🔄 输入输出格式:
  输入格式:   自然语言（中/英）、Markdown、JSON、文件流
  输出格式:   Markdown（默认）、纯文本、文件、API 调用
  编码:       UTF-8
  最大输入:   ~200K tokens（上下文窗口限制）
```

**生活类比**：
- 这就像餐厅的"菜单"——你看到菜单（输入）就知道能点什么，菜端上来（输出）就知道会得到什么
- 如果菜单上写了"牛排"，端上来却是"鱼"，那就是接口出了问题

### 5️⃣ 协作对象 — Collaboration（与谁合作）

学习助手 Agent 不是一个人战斗，它需要跟很多"同事"配合：

```
协作网络:

  用户 (Luvia)
     │
     ▼
  ┌─────────────────────────────┐
  │    学习助手 Agent (Hermes)    │
  │    "我是总调度中心"            │
  └─────────────────────────────┘
     │        │         │        │
     ▼        ▼         ▼        ▼
  ┌─────┐ ┌──────┐ ┌───────┐ ┌────────┐
  │ LLM │ │ 文件  │ │ GitHub│ │ 浏览器  │
  │ API │ │ 系统  │ │ CLI   │ │ 搜索   │
  └─────┘ └──────┘ └───────┘ └────────┘
     │        │         │        │
     ▼        ▼         ▼        ▼
  思考推理  读写笔记  推送代码  查找资料
```

**每个协作对象的角色：**

| 协作对象 | 做什么 | 怎么合作 | 失败时怎么办 |
|---------|--------|---------|-------------|
| LLM API | 帮 Agent "思考" | HTTP API 调用 | 重试 / 切换模型 |
| 文件系统 | 读写笔记文件 | 本地文件操作 | 检查路径权限 |
| GitHub CLI | 推送代码到仓库 | `gh` 命令行 | 检查认证 token |
| 浏览器搜索 | 查找最新资料 | Web Search API | 换搜索引擎 |
| Obsidian | 管理知识库 | 本地文件夹同步 | 检查 vault 路径 |
| Telegram | 接收/发送消息 | Bot API | 重连 / 报错 |

### 6️⃣ 如何被调用 — Invocation（调用方式）

```
调用方式:

  方式 1: 直接对话 💬
    用户 → Telegram → Agent 收到消息 → 思考 → 回复

  方式 2: 定时任务 ⏰
    Cron Job → Agent 自动执行 → 把结果推送给用户

  方式 3: API 调用 🔌
    其他程序 → Agent API → Agent 处理 → 返回结果

  方式 4: 事件触发 🔔
    GitHub 有新 Issue → Webhook → Agent 自动处理 → 回复

调用协议:
  ├── 本地调用:   stdio（标准输入输出）
  ├── 远程调用:   HTTP / WebSocket
  ├── 协议:      MCP（Model Context Protocol）
  └── 认证:      API Key + 本地权限
```

**生活类比**：
- 方式 1 = 你直接走进店里跟店员说话
- 方式 2 = 你设了一个闹钟，到点自动响
- 方式 3 = 你打电话叫外卖
- 方式 4 = 门铃响了，有人来找你

### 7️⃣ 失败如何处理 — Failure & Recovery（失败与恢复）

这是最容易被忽略但**最重要**的部分——Agent 一定会出错，关键是出错后怎么办。

```
失败分类与处理策略:

┌──────────────────┬─────────────────────┬──────────────────────┐
│ 失败类型          │ 发生了什么            │ 怎么处理              │
├──────────────────┼─────────────────────┼──────────────────────┤
│ 🔴 LLM 幻觉      │ Agent 编造了不存在    │ 输出带"⚠️ 需验证"     │
│                  │ 的论文/数据           │ 标记，提醒用户核实     │
├──────────────────┼─────────────────────┼──────────────────────┤
│ 🟡 API 超时       │ LLM 服务暂时不可用   │ 自动重试 3 次 →       │
│                  │                     │ 切换备用模型          │
├──────────────────┼─────────────────────┼──────────────────────┤
│ 🟡 理解错误       │ Agent 误解了用户意图  │ 反问确认："你是说     │
│                  │                     │ XX 吗？"              │
├──────────────────┼─────────────────────┼──────────────────────┤
│ 🔴 工具调用失败    │ GitHub push 失败     │ 记录错误日志 →        │
│                  │                     │ 告知用户手动处理       │
├──────────────────┼─────────────────────┼──────────────────────┤
│ 🟡 上下文溢出      │ 对话太长，超出窗口    │ 自动总结历史 →        │
│                  │ 限制                 │ 压缩上下文继续        │
├──────────────────┼─────────────────────┼──────────────────────┤
│ 🔴 安全越界       │ 请求超出权限范围      │ 拒绝执行 → 告知原因    │
│                  │ （如转账）            │ → 建议替代方案        │
└──────────────────┴─────────────────────┴──────────────────────┘

失败处理原则（类似金融风控）:
  1. 🛡️ 最小损失原则   → 宁可不做，不要做错（拒绝 > 搞砸）
  2. 📋 可追溯原则     → 每次失败都记录日志（链上 or 本地）
  3. 🔔 及时通知原则   → 出了问题第一时间告知用户
  4. 🔄 自动恢复原则   → 能重试的自动重试，不能的才报告
```

**生活类比**：
- 这就像开车时的"防御性驾驶"——你不是在想"怎么撞车"，而是在想"如果前面突然有人冲出来，我该怎么办"
- Agent 的失败处理 = 给 Agent 装上"安全气囊"

## 五、可选加分：MCP vs A2A 协议对比

我选择对比 **MCP（Model Context Protocol）** 和 **A2A（Agent-to-Agent）** 这两个协议。

### 🔍 它们分别是什么？

#### MCP — Model Context Protocol（模型上下文协议）

**一句话理解**：给 AI Agent 装上"万能插头"🔌——让 Agent 能像插 USB 一样连接各种工具和数据源。

**它解决的是哪类问题？** → **Agent 与工具之间的接口标准化**

没有 MCP 时：
```
Agent 想用 GitHub → 需要写专门的 GitHub 代码
Agent 想用数据库 → 需要写专门的数据库代码
Agent 想用浏览器 → 需要写专门的浏览器代码
每接一个工具，都要重新写一套对接代码 😩
```

有 MCP 后：
```
Agent 想用任何工具 → 插上 MCP 插头 → 自动识别工具能力 → 直接使用
就像 USB 接口：不管你插的是键盘、鼠标还是U盘，都是同一个口 🔌
```

**生活类比**：
- 没有 MCP = 每种电器需要不同的插座，你得装 10 种插座
- 有 MCP = 万能插座，所有电器插上去就能用

**适合解决的问题**：
- Agent 需要调用外部工具（搜索、文件、API）
- 多个工具之间的接口不统一
- 需要"即插即用"地扩展 Agent 能力

---

#### A2A — Agent-to-Agent Protocol（Agent 间协作协议）

**一句话理解**：给 Agent 之间建一条"对话通道"📞——让不同的 Agent 能互相沟通、分工合作。

**它解决的是哪类问题？** → **Agent 与 Agent 之间的协作标准化**

没有 A2A 时：
```
研究 Agent 做完调研 → 不知道怎么把结果交给写作 Agent
写作 Agent 写完文章 → 不知道怎么把文章交给发布 Agent
每个 Agent 都是"孤岛" 🏝️
```

有 A2A 后：
```
研究 Agent → A2A 协议 → 写作 Agent → A2A 协议 → 发布 Agent
就像一条流水线：每个工人做好自己那一步，然后传给下一个工人 🏭
```

**生活类比**：
- 没有 A2A = 一群人各干各的，互相不说话，效率很低
- 有 A2A = 像一支足球队⚽——守门员、后卫、前锋各有分工，但通过传球（协议）配合完成进攻

**适合解决的问题**：
- 多个 Agent 需要协作完成复杂任务
- Agent 之间需要传递上下文、状态、结果
- 需要"任务分包"——大 Agent 把任务拆给小 Agent

---

### 📊 核心对比

```
              MCP                         A2A
         ┌──────────────┐           ┌──────────────┐
  定位    │ Agent ↔ 工具  │           │ Agent ↔ Agent │
         │ （垂直连接）   │           │ （水平协作）   │
         └──────────────┘           └──────────────┘

  解决    │ "我怎么用这个  │           │ "我怎么跟另一个│
  什么    │  工具？"       │           │  Agent 配合？" │
         └──────────────┘           └──────────────┘

  类比    │ USB 接口       │           │ 足球队传球     │
         │ （插上就能用）   │           │ （分工配合）    │
         └──────────────┘           └──────────────┘

  层级    │ 单个 Agent 内部 │           │ 多个 Agent 之间│
         │ 的能力扩展      │           │ 的任务协作     │
         └──────────────┘           └──────────────┘
```

### 🔗 它们的关系：不是二选一，而是配合使用

```
                    ┌─────────────────────────────┐
                    │     复杂任务（如写研究报告）     │
                    └─────────────────────────────┘
                                  │
                          A2A 协议拆分任务
                          ╱              ╲
                         ▼                ▼
              ┌──────────────┐   ┌──────────────┐
              │  调研 Agent    │   │  写作 Agent    │
              └──────────────┘   └──────────────┘
                   │                    │
             MCP 调用工具          MCP 调用工具
              ╱    ╲                ╱    ╲
             ▼      ▼              ▼      ▼
         ┌─────┐ ┌─────┐      ┌─────┐ ┌─────┐
         │搜索 │ │数据库│      │图表 │ │翻译  │
         └─────┘ └─────┘      └─────┘ └─────┘
```

**一句话总结**：
> **MCP 让 Agent 能"做事"（连接工具），A2A 让 Agent 能"合作"（连接彼此）。**
> 就像一个人既需要学会使用工具（MCP），也需要学会跟同事沟通（A2A），才能在团队里发挥作用。

## 六、核心洞察 💡

### 为什么 Agent Profile 在 Web3 世界更重要？

**在 Web2 世界**：
- Agent 的身份由平台说了算（微信的机器人、钉钉的助手）
- 你只能在平台内部使用 Agent
- 平台倒了，Agent 就没了

**在 Web3 世界**：
- Agent 有自己的链上身份（不依赖任何平台）
- 你可以在任何地方调用任何 Agent（跨平台、跨应用）
- Agent 的信誉、能力、历史都记录在链上（可验证、可迁移）

### 一句话总结

> **Agent Profile = Agent 的"数字身份证 + 简历 + 使用说明书"**
> 没有 Profile 的 Agent 就像没有身份证的人——你不知道它是谁、能做什么、能不能信任它。
> 在 Agent 越来越多的未来，Profile 就是 Agent 世界的"基础设施"。
