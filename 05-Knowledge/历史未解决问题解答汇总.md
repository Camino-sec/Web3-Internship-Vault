## 一、Harness Engineering 相关（5/27 笔记）

### Q1: Harness Engineering 的六大项具体包含哪些详细内容？

你在 5/27 的笔记里其实已经记录了这六大支柱（来自小红书评论）。现在展开讲每个：

**六大支柱详解**：

1. **Intent Alignment（意图对齐）**
   - **是什么**：确保 AI 理解的「任务」和人类真正想要的「结果」一致
   - **类比**：你跟出租车司机说「去最近的医院」，你其实想去的是口腔医院而不是急诊中心——意图对齐就是让 AI 不要「好心办坏事」
   - **技术实现**：system prompt 设计、few-shot examples、constraint specification

2. **Least Privilege（最小权限）**
   - **是什么**：AI 只能用完成任务所需的最少权限
   - **类比**：你去图书馆借书，只需要借书卡，不需要给你校长的门禁卡
   - **技术实现**：工具白名单、路径安全（s02 的 `safe_path()`）、API scope 限制

3. **Policy Compliance（策略合规）**
   - **是什么**：AI 的每一步操作都必须符合预设的规则
   - **类比**：公司报销制度——你不能随便花钱，必须按流程来
   - **技术实现**：pre-tool hook 检查、规则引擎、constitutional AI

4. **Audit Trail（审计追踪）**
   - **是什么**：记录 AI 做的每一件事，事后可以复盘
   - **类比**：银行的每笔交易都有流水记录，出了问题可以追溯
   - **技术实现**：Trace 系统（s01-s02 的消息日志）、structured logging

5. **Sandbox Isolation（沙盒隔离）**
   - **是什么**：AI 在一个封闭环境里操作，不能影响外面的世界
   - **类比**：小孩子玩的沙盘——可以在里面随便玩，但沙子不会跑到外面
   - **技术实现**：Docker 容器、虚拟机、路径安全函数

6. **Human-in-the-Loop（人类在环）**
   - **是什么**：关键决策必须人类确认
   - **类比**：自动驾驶汽车遇到复杂路况时，会提醒人类接管方向盘
   - **技术实现**：s03 的 Permission 系统、approval hooks、权限分级

> 💡 **六大支柱 vs ETCLOVG 七层**：六大支柱更偏「安全治理」视角（怎么防），ETCLOVG 更偏「工程实现」视角（怎么做）。两者互补，不是替代关系。

### Q2: 隐私构建器（Privacy Builder）具体怎么用？

**是什么**：W3PN（Web3 Privacy Now）开发的免费开源工具，帮助 builder 在项目中集成隐私保护。

**五个模块**：
- **词汇表**：隐私领域专业术语解释
- **工具库**：按场景分类的隐私工具推荐（加密通信、匿名交易、数据保护等）
- **创意生成器**：根据你的项目类型，生成隐私保护方案建议
- **案例库**：真实项目的隐私实现参考
- **框架**：隐私设计的系统化方法论

**怎么用**：
1. 访问 W3PN 官网（web3privacy.info）
2. 选择你的项目类型（DeFi、DAO、Social 等）
3. 用创意生成器获取隐私方案建议
4. 在工具库中找到具体工具
5. 参考案例库了解最佳实践

**和 EIV 的关系**：EIV 用 ERC-8004 做 attestation，本质上是在「可验证」和「隐私保护」之间找平衡——验证执行结果的同时，不一定需要暴露全部执行细节。

### Q3: Agent 的隐式记忆（向量数据库 + 知识图谱）现在进化到什么程度了？

**三种记忆的进化路线**：

| 阶段 | 技术 | 现状 | 类比 |
|------|------|------|------|
| 1.0 显式记忆 | `.cursorrules` / `memory-bank.md` | ✅ 已普及 | 手写笔记本 |
| 1.5 自动显式记忆 | AI 自己更新 `.cursorrules` | ✅ Claude Code 已支持 | 日记本会自动更新 |
| 2.0 隐式记忆 | 向量数据库（RAG） | ✅ 已商用 | 用搜索引擎查资料 |
| 2.5 知识图谱 | Graph RAG | 🔄 发展中 | 脑中的知识网络 |
| 3.0 自发蒸馏 | Fine-tuning 从经验中学习 | 🔬 实验阶段 | 肌肉记忆/直觉 |

**当前最有意思的趋势**：
- **Cursor / Claude Code** 的 `.cursorrules` 本质上就是 1.0 阶段的记忆
- **Graph RAG**（知识图谱 + 向量检索）正在取代纯向量检索，因为知识图谱能保留「A 导致 B」的因果关系，而向量只能找到「A 和 B 相似」
- **自发蒸馏**最前沿：Agent 跑了 100 个任务后，用这些经验 fine-tune 自己，变成「下意识的直觉」

> 💡 你在 5/28 的笔记里已经用费曼学习法解释了这个概念：「隐式记忆 = 骑自行车的肌肉记忆，显式记忆 = 手机里的通讯录」。这个理解是准确的。

### Q4: 滑点保护具体怎么设置？

**类比回忆**：你去拍卖会，出价 100 元买东西，但等轮到你时价格涨到了 102 元——那 2 元就是「滑点」。

**滑点保护 = 设置「最高容忍价格偏差」**

**在 DEX（去中心化交易所）中的设置**：
1. **Uniswap / PancakeSwap** 界面上通常有个齿轮图标 ⚙️
2. 点进去可以看到「Slippage Tolerance」选项
3. 常见设置：
   - **0.1%**：稳定币交易（USDT↔USDC，价格几乎不变）
   - **0.5%**：主流代币交易（ETH↔USDC）
   - **1-3%**：波动大的小币种
   - **>5%**：极端情况，容易被 MEV 机器人攻击

**代码层面（智能合约）**：
```solidity
// 在 swap 调用时指定最小输出量
uint amountOutMin = amountOut * (100 - slippagePercent) / 100;
router.swapExactTokensForTokens(
    amountIn,
    amountOutMin,  // ← 这就是滑点保护
    path,
    to,
    deadline
);
```

**和 EIV 的关系**：如果 EIV 的 Agent 需要自动执行 DeFi 交易，滑点保护是必须内置的安全机制——Agent 不能接受「无论多贵都买」。

### Q5: Agent Teams 的 Hooks 具体怎么配置？

**Hook = 在特定事件发生时自动执行的「插件」**

**类比**：就像你设置了「每天早上 7 点闹钟」——闹钟就是一个 Hook，触发条件是「时间到了 7 点」，动作是「响铃」。

**Agent Teams 的三种核心 Hook**：

1. **TeammateIdle Hook（队友空闲时）**
   - **触发**：当一个队友完成任务后没事做
   - **动作**：自动给它分配下一个任务
   - **配置示例**：
   ```python
   hooks:
     - event: teammate_idle
       action: assign_next_task
       priority: by_skill_match
   ```

2. **TaskCreated Hook（新任务创建时）**
   - **触发**：当 Lead 创建一个新任务
   - **动作**：根据技能匹配自动分配给最合适的队友
   - **配置示例**：
   ```python
   hooks:
     - event: task_created
       action: auto_assign
       criteria: skill_match
   ```

3. **TaskCompleted Hook（任务完成时）**
   - **触发**：当队友报告任务完成
   - **动作**：自动检查质量（跑测试、检查代码规范）
   - **配置示例**：
   ```python
   hooks:
     - event: task_completed
       action: quality_gate
       checks:
         - run_tests
         - lint_check
         - coverage_threshold: 80
   ```

**配置位置**：通常在 `.claude/teams/` 目录下的 YAML 配置文件中。

> 💡 你已经在 5/27 的笔记里记录了 Hook 的节点类型（Pre-tool、Post-tool、Inter-agent、Stop/Pause）和熔断机制。Agent Teams 的 Hook 是在这个基础上的扩展——从单个 Agent 的 Hook 升级到团队级别的事件驱动。

## 二、工具机制相关（5/28 笔记）

### Q7: 工具的 input_schema 具体怎么定义

**input_schema = 给 AI 写的「工具使用说明书」**

**类比**：你去餐厅点菜，菜单上写着「宫保鸡丁：鸡肉+花生+辣椒，微辣/中辣/特辣可选」——这就是 input_schema，告诉 AI 这个工具接受什么参数、什么格式。

**具体格式（JSON Schema）**：
```json
{
    "name": "read_file",
    "description": "读取指定路径的文件内容",
    "input_schema": {
        "type": "object",
        "properties": {
            "path": {
                "type": "string",
                "description": "文件路径，如 './test.py'"
            },
            "offset": {
                "type": "integer",
                "description": "从第几行开始读"
            }
        },
        "required": ["path"]
    }
}
```

**核心字段**：
- `name`：工具名称
- `description`：告诉 AI 这个工具干什么
- `input_schema.properties`：每个参数的类型和说明
- `input_schema.required`：哪些参数是必填的

**Anthropic vs OpenAI 的区别**：
- Anthropic 用 `input_schema`
- OpenAI 用 `parameters`
- 底层都是 JSON Schema，只是字段名不同

### Q8: 多个工具调用时的并发/串行机制

**类比**：你做饭时——
- **串行**：先切菜 → 切完了 → 再炒菜（一步完了才走下一步）
- **并发**：一边煮饭一边炒菜（两个炉子同时开火）

**谁决定并发还是串行？→ 是 AI 模型自己决定的**

**串行场景**（AI 有依赖关系）：
```
Turn 1: AI 调用 read_file → 拿到文件内容
Turn 2: AI 根据内容调用 edit_file → 修改文件
```
（第二步依赖第一步的结果，必须串行）

**并发场景**（AI 无依赖关系）：
```
Turn 1: AI 同时调用 [read_file("a.py"), read_file("b.py")]
→ Harness 并行执行两个读取，一起返回结果
```
（两个文件互不影响，可以同时读）

**Harness 的实现**：
- 检测 AI 返回的响应中有几个 `tool_use` block
- 如果有多个且无依赖 → 用线程池/asyncio 并发执行
- 如果有依赖 → 自动串行
- 部分 Harness 有 `max_parallel_tools` 限制并发数

### Q9: Harness 如何给 AI 打分

**类比**：老师改考卷有不同方式——

| 打分方式 | 类比 | 适用场景 |
|----------|------|----------|
| **测试用例** | 数学题对答案 | 代码生成（跑测试看通不通过） |
| **输出匹配** | 填空题比对标准答案 | 问答任务（答案是否在回复里） |
| **LLM-as-Judge** | 请另一个老师打分 | 开放式任务（创意写作、分析） |
| **状态检查** | 检查实验结果 | 操作任务（文件是否创建成功） |
| **多维度加权** | 综合考试（笔试40%+面试30%+实验30%） | 复杂 Agent 任务 |

**核心思想**：
> Harness 不是「看 AI 说了什么」，而是「看 AI **做了什么**以及**结果对不对**」。

**知名 Harness 框架**：
- **SWE-bench**：给 AI 真实 GitHub issue，看能否修好 bug
- **HumanEval**：代码生成，跑 164 道编程题
- **SWE-bench Verified**：人工验证过的 SWE-bench 子集

### Q12: pitch 脚本怎么写——非技术人员讲技术项目的最佳叙事结构

**非技术 pitch 的黄金公式：问题 → 方案 → 价值 → 展示**

**EIV 的 pitch 脚本框架**（5 分钟版）：

```
1. 开场（30秒）
   「你们有没有遇到过 AI Agent 帮你执行任务，但你不确定它到底做没做对？」
   → 用一个生活场景引起共鸣

2. 问题（60秒）
   「现在 AI Agent 能操作资金、调用 API、写代码...
    但执行结果的可信度怎么验证？
    你信它说的「已完成」吗？」
   → 强调「信任赤字」

3. 方案（90秒）
   「EIV 是一个执行完整性验证器。
    它用 ERC-8004 标准在链上记录 AI 的每一步执行，
    任何人可以独立验证结果的正确性。」
   → 用「银行流水」类比 attestation

4. 价值（60秒）
   「对用户：不再盲信 AI，可以验证
    对开发者：一行代码集成，提升 Agent 可信度
    对行业：建立 AI 执行的信任基础设施」
   → 三个层面的价值

5. 展示（60秒）
   演示 eiv-core 跑通一个验证流程
   展示 dashboard 的结果可视化
   → 让观众「看到」而不是「听到」

6. 收尾（30秒）
   「AI Agent 的时代已经来了，
    信任不再是选择题，而是必答题。
    EIV 就是这道题的答案。」
```

**非技术人员讲技术的三个秘诀**：
1. **用类比，不用术语**：「attestation」→「银行流水」
2. **讲人话，讲故事**：「一个 AI Agent 帮你转了 1000 USDT，你收到了 950」
3. **展示实物，不讲原理**：让观众看到 dashboard，而不是看代码
