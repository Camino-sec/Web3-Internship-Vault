# PART 01：AI 开发方法论

## 1. 什么叫从 0 到 1？

> 0→1 的代码未必多，难点是**准确找到值得验证的核心问题**。

| 阶段 | 定义 | 关键特征 |
|------|------|---------|
| **0 → 1** | 证明核心价值的 Demo | 面向明确用户与场景；核心体验能走通；清楚展示"解决了什么问题"；允许模拟数据或人工协助 |
| **1 → 99** | 把 Demo 变成系统 | 覆盖更多场景和边界；补齐可靠性、安全、性能；建立发布、运营、合规能力 |

**关键认知**：0→1 不是写很多代码，而是用最少的代码验证"这件事值不值得做"。

---

## 2. AI 开发的两大优势

### 降低开发门槛
- 快速解释陌生代码和技术概念
- 生成原型、脚手架与常见功能
- 帮助非专家跨过早期工具和语法障碍
- ⚠️ 门槛降低 ≠ 工程责任降低

### 提升开发效率
- 功能迭代和缺陷修复反馈更快
- 测试、文档与迁移可同步推进
- 理解旧代码和实施重构的成本下降
- 可并行探索多个方案，再由人取舍

> **核心洞察**：真正的收益不是少写代码，而是**更快获得可信反馈**。

## 3. AI Agent：从回答问题到执行任务

**定义**：AI Agent 是运行在特定环境中的目标驱动系统——基于目标、上下文与约束选择行动，观察结果并更新状态，循环执行，直到完成目标或需要人工介入。

```
目标 → 感知 → 规划 → 行动 → 评估 → 循环
```

**公式拆解**：
> Agent = 模型 + 上下文 + 记忆 + 工具 + 执行循环 + 权限边界 + 验证

核心是把推理转化为**受约束、可观察、可验证的行动**。

### 为什么 Agent 能力提升这么快？

| 驱动因素 | 说明 |
|---------|------|
| 模型更强 | 推理、代码理解和多步骤规划持续提升 |
| 上下文更长 | 能读取更多代码、文档、历史和中间结果 |
| 工具更丰富 | CLI、浏览器、代码执行、MCP 与外部 API |
| 闭环更完整 | 持久化指令、权限、测试和评估提升可靠性 |

> 能力增长来自"更聪明的模型"与"更完整的行动系统"**共同演进**。

## 4. 三个关键工程实践

### 📌 AGENTS.md：把长期规则写进项目

| 层级 | 位置 | 用途 |
|------|------|------|
| 用户/全局级 | `~/.claude/CLAUDE.md` 或 `~/.codex/AGENTS.md` | 跨项目复用的个人偏好与工作方式 |
| 项目/目录级 | 项目根目录的 `AGENTS.md` | 构建、测试命令；架构边界；编码约定；交付标准 |

**注意**：不要写入密钥或临时需求；只记录**稳定、可复用、需要长期执行的规则**。

### 📌 TDD（测试驱动开发）

```
写测试 → 测试失败 → 最小实现 → 测试通过 → 重构
  RED    →    GREEN    →   REFACTOR
```

**为什么特别适合 AI 编程？**
- 把"正确"转化为可执行的验收标准
- 让 Agent 在生成过程中快速自我纠正
- 防止修复当前问题时破坏既有行为

⚠️ 测试只能证明被覆盖的行为。集成、安全和人工体验仍不可缺少。

### 📌 SDD（规范驱动开发）

```
需求(为什么做) → 规范(做成什么) → 方案(如何实现) → 任务(如何拆分) → 实现(代码测试) → 归档(保留结果)
```

**核心价值**：
- 记录意图、约束、决策和验收标准
- 约束 Agent 的实施过程，减少方向漂移
- 让代码、任务和验证结果可以追踪

**工具参考**：新项目用 Spec Kit；已有项目用 OpenSpec 管理增量变更。

---

## 5. 跟着 AI 一起提升四项能力

| 能力 | 核心问题 | 说明 |
|------|---------|------|
| **会描述** | 问题是什么？完成证据是什么？ | 把想法写成目标、用户、场景、约束和验收标准 |
| **会拆解** | 依赖和风险在哪？每一步产出什么？ | 把复杂任务分成可执行、可理解、可验证的小步骤 |
| **会验证** | 主要风险覆盖了吗？失败时能回滚吗？ | 用测试、审查、日志和真实体验判断结果是否可信 |
| **会设计** | 系统边界合理吗？规则能长期复用吗？ | 设计架构边界、数据流、协作规则和长期质量体系 |

> **最终提升的不是提示词技巧，而是定义问题、组织工作、验证结果和设计系统的工程能力。**

# PART 02：Web3 技术栈

## 1. 区块链是什么？

> 区块链是一类由**多节点共同维护**、通过**密码学与共识**验证状态转换的**复制状态机/分布式账本**。参与者无需共同信任单一中心，也能对交易顺序和系统状态形成**可验证的一致结果**。

| 特征 | 说明 |
|------|------|
| 密码学验证 | 哈希、签名和承诺保证数据可验证 |
| 点对点复制 | 节点传播交易、区块和状态信息 |
| 共识与最终性 | 协议决定有效链，并逐步确认结果 |
| 确定性执行 | 相同输入按规则得到相同状态转换 |

⚠️ 准确表述：公开链通常提供确定性状态转换与协议/经济最终性；确认前仍可能发生短暂重组，不能简单称为传统强一致性。

---

## 2. Web3 开发的五个主要方向

| 方向 | 核心职责 | 一句话概括 |
|------|---------|-----------|
| **DApp 开发** | 用户界面、钱包连接与链上数据 | 用户看到和交互的一切 |
| **智能合约** | 链上状态、资产与协议规则 | 写在链上的"法律" |
| **钱包开发** | 密钥、账户、签名与交易体验 | 用户的"数字身份"入口 |
| **节点开发** | P2P、执行、共识、存储与 RPC | 区块链的"发动机" |
| **安全审计** | 威胁建模、测试、审计与监控 | 系统的"体检医生" |

> 五个方向**共享区块链、密码学、网络、测试和安全基础**。

---

## 3. 共同基础一：密码学与密钥体系

| 类别 | 技术栈 |
|------|--------|
| 哈希 | Keccak-256 / SHA-256 / Merkle Tree |
| 签名 | ECDSA · secp256k1 · EdDSA（按链） |
| 钱包 | BIP-39 · BIP-32 · BIP-44 |
| 加密 | 非对称加密 · KDF · 安全随机数 |

**学习重点**：
- 理解单向性、抗碰撞与数据完整性
- 理解私钥、公钥、地址和数字签名
- 掌握助记词、分层确定性钱包与密钥派生
- 知道随机数、密钥存储和备份为何关键

**练习**：从随机熵生成助记词和账户，完成消息签名、验签与地址派生。

---

## 4. 共同基础二：区块链运行原理

```
账户与状态 → 交易 → 区块 → 共识 → 执行环境 → 开发接口
```

| 模块 | 核心内容 |
|------|---------|
| 账户与状态 | 余额、Nonce、合约存储 |
| 交易 | 签名、Gas、调用数据 |
| 区块 | 排序、执行结果、状态根 |
| 共识 | 分叉选择、证明与最终性 |
| 执行环境 | EVM / WASM 与状态转换 |
| 开发接口 | JSON-RPC、事件与回执 |

> **核心模型**：交易是输入，执行规则产生状态转换，共识决定全网接受哪一组有序状态转换。

## 5. 五个方向的技术栈详解

### 方向一：DApp 开发
| 类别 | 技术栈 |
|------|--------|
| 前端 | TypeScript · React / Next.js |
| 交互 | viem / ethers · wagmi · WalletConnect |
| 接口 | ABI · JSON-RPC · WebSocket |
| 数据 | Events · Indexer · The Graph |
| 质量 | Unit / E2E · 交易状态机 · Monitoring |

**作品要求**：实现连接钱包、交易模拟、签名、广播、确认和事件展示的完整闭环。

### 方向二：智能合约开发
| 类别 | 技术栈 |
|------|--------|
| EVM | Solidity / Vyper |
| 其他链 | Rust（Solana 等生态，不能与 EVM 混用） |
| 工具 | Foundry / Hardhat · Anvil |
| 组件 | OpenZeppelin Contracts |
| 验证 | Fuzz · Invariant · Fork Test · Verification |

**学习顺序**：基础合约 → 权限与金库 → DeFi 原语 → 协议级测试与安全设计。

### 方向三：钱包开发
| 类别 | 技术栈 |
|------|--------|
| 密钥 | BIP-39 · BIP-32/44 · HSM / MPC |
| 签名 | secp256k1 · EIP-191 · EIP-712 |
| 连接 | EIP-1193 · EIP-6963 · WalletConnect |
| 账户抽象 | ERC-4337 · Smart Account |
| 安全 | Transaction Simulation · Permission Management |

**作品要求**：测试网钱包，完成账户创建、类型化签名、交易模拟、广播与恢复流程。

### 方向四：节点开发
| 类别 | 技术栈 |
|------|--------|
| 语言 | Go · Rust · Java · C++ · TypeScript（按客户端） |
| 网络 | libp2p / devp2p · Gossip · Discovery |
| 执行 | EVM · State DB · Transaction Pool |
| 共识 | Fork Choice · Finality · Validator |
| 运维 | Linux · Docker / systemd · Prometheus / Grafana |

**建议路径**：先运行测试网节点并观察同步、重组和资源使用，再尝试修改客户端代码。

### 方向五：安全审计
| 类别 | 技术栈 |
|------|--------|
| 分析 | Manual Review · Slither · Dependency Scan |
| 动态 | Fuzz · Invariant · Fork Test |
| 形式化 | Symbolic Execution · Formal Verification（按风险） |
| 标准 | OWASP SCSVS / Smart Contract Top 10 |
| 运营 | On-chain Monitoring · Alert · Incident Response |

> 工具只能提供证据；最终结论必须来自**威胁模型、人工判断和可复现验证**。

## 6. 开发者视角下的 ETH 系统

```
DApp · 钱包 · 后端服务 · 索引器
        ↓ JSON-RPC / WebSocket
┌──────────────────┐    ┌──────────────────┐
│   执行客户端      │    │   共识客户端      │
│ · EVM 执行交易    │    │ · 权益证明共识     │
│ · 维护账户状态    │◄──►│ · 分叉选择        │
│ · 交易池 + RPC   │    │ · 最终性验证      │
└──────────────────┘    └──────────────────┘
        Engine API 连接
```

- **执行客户端**：执行交易与智能合约（EVM），提供 JSON-RPC 接口
- **共识客户端**：参与权益证明共识，验证者负责提议区块与提交证明
- 完整节点通常**同时运行**执行客户端和共识客户端

---

## 7. 一笔交易如何穿过 ETH 系统

```
构造 → 模拟 → 签名 → 广播 → 执行 → 共识 → 读取
 DApp   估算    钱包    RPC    EVM    区块    回执
 编码   Gas    确认   交易池  状态   最终性   索引
```

**调试路径**：交易哈希 → 回执/状态 → 事件日志 → 调用轨迹 → 所在区块 → 确认与最终性

> 每个 Web3 开发方向，都在这条链路上负责不同的一段。
