## 二、Agent Wallet 权限策略设计

### 2.1 场景设定

> **场景**：一个 AI Agent 帮助用户管理测试网上的小额 DeFi 资产。
> Agent 可以自动执行「低风险的日常操作」（如再平衡、领取奖励），
> 但任何「超出预设边界」的操作都需要用户确认。

### 2.2 权限策略全景

#### A. 预算控制（Budget Control）

| 参数 | 值 | 说明 |
|------|-----|------|
| 单次交易上限 | 10 USDC（测试网） | 超过此金额需人工确认 |
| 日累计上限 | 50 USDC | 24 小时内 Agent 自动执行的总额 |
| 周累计上限 | 200 USDC | 7 天滚动窗口 |
| Gas 预算 | 0.01 ETH/日 | Agent 每日可用的 gas 总量 |
| 超额行为 | 自动拒绝 + 通知用户 | 不允许静默超支 |

#### B. 可调用合约白名单（Contract Whitelist）

| 合约类型 | 示例 | 允许的操作 |
|---------|------|-----------|
| DEX Router | Uniswap V3 Router（测试网） | swap（限白名单 token 对） |
| Lending | Aave V3 Pool（测试网） | supply, withdraw |
| Staking | Lido（测试网） | stake, claimRewards |
| Token | USDC, WETH（测试网） | approve（限额内）, transfer |

**不在白名单的合约 → 自动拒绝，需用户手动添加。**

#### C. 可执行动作（Allowed Methods）

| 动作类型 | 允许？ | 条件 |
|---------|--------|------|
| 查询余额/价格 | ✅ 自动 | 只读，无限制 |
| swap（同价值资产） | ✅ 自动 | 白名单 token 对 + 金额 < 阈值 |
| supply / withdraw | ✅ 自动 | 白名单协议 + 金额 < 阈值 |
| claimRewards | ✅ 自动 | 仅白名单协议 |
| approve（授权新合约） | ⚠️ 需确认 | 必须用户明确授权 |
| approve（无限额） | 🔴 禁止 | Agent 永远不能发起无限授权 |
| transfer（大额） | 🔴 需人工签名 | > 单次限额 |
| 部署合约 | 🔴 禁止 | Agent 无权部署 |
| 治理投票 | 🔴 需人工签名 | 影响协议参数 |

#### D. 人工确认阈值（Human Confirmation Threshold）

```
┌─────────────────────────────────────────────┐
│           确认等级划分                        │
├─────────────────────────────────────────────┤
│                                             │
│  🟢 自动执行（无需确认）                      │
│  ├── 金额 < 5 USDC                          │
│  ├── 白名单合约 + 白名单方法                  │
│  └── 当日累计 < 30 USDC                      │
│                                             │
│  🟡 通知 + 简单确认（一句话/按钮确认）         │
│  ├── 金额 5-10 USDC                         │
│  ├── 新的 token 对 swap                      │
│  └── 当日累计 30-50 USDC                     │
│                                             │
│  🔴 必须人工签名（钱包弹窗确认）               │
│  ├── 金额 > 10 USDC                         │
│  ├── 任何 approve 操作                       │
│  ├── 合约不在白名单                          │
│  ├── 调用方法不在允许列表                     │
│  └── 当日累计 > 50 USDC                      │
│                                             │
└─────────────────────────────────────────────┘
```

#### E. 撤销方式（Revocation）

| 撤销手段 | 触发条件 | 执行方式 |
|---------|---------|---------|
| Session Key 过期 | 到达设定的过期时间 | 自动失效，无需操作 |
| 主动撤销 Session Key | 用户随时可以 | 调用 Smart Account 的 `revokeSessionKey()` |
| 暂停 Agent 权限 | 用户一键暂停 | 调用 Safe 的 `disableModule()` |
| 紧急冻结 | 发现异常交易 | Safe guard 触发紧急暂停 |
| 撤销 token 授权 | 用户主动或检测到风险 | 调用 token 合约的 `approve(address, 0)` |

**设计原则**：撤销应该比授权更容易操作。用户应该能在 1 步内暂停 Agent 的所有权限。

#### F. 日志记录（Logging）

每一步操作都必须记录到可审计的日志中：

```
Agent 执行日志格式：
{
  "timestamp": "2026-05-31T15:30:00Z",
  "action": "swap",
  "agent_session_key": "0x...（地址，非私钥）",
  "target_contract": "0x...",
  "method": "swapExactTokensForTokens",
  "params": { "amountIn": "5000000", "tokenIn": "USDC", "tokenOut": "WETH" },
  "risk_level": "GREEN",
  "auto_executed": true,
  "tx_hash": "0x...",
  "gas_used": "150000",
  "gas_cost": "0.003 ETH",
  "result": "success",
  "balance_before": { "USDC": "100.00", "WETH": "0.50" },
  "balance_after": { "USDC": "95.00", "WETH": "0.502" }
}
```

**日志必须包含**：
- **谁**：Session Key 地址（不是私钥！）
- **什么**：调用的合约、方法、参数
- **多少**：涉及的金额
- **什么时候**：精确时间戳
- **结果**：成功/失败 + tx hash
- **余额变化**：操作前后的资产对比

#### G. 失败处理（Failure Handling）

| 失败类型 | 自动处理 | 需要人工 |
|---------|---------|---------|
| Nonce 冲突 | ✅ 自动用新 nonce 重试 | — |
| Gas 不足 | ✅ 自动提高 gas（在预算内） | 超出 gas 预算则通知用户 |
| 滑点超限 | ✅ 自动取消，记录日志 | — |
| 合约 revert | — | ✅ 通知用户 + 展示 revert 原因 |
| 余额不足 | — | ✅ 通知用户充值 |
| 合约暂停 | — | ✅ 通知用户 + 暂停相关自动操作 |
| 连续失败 3 次 | — | ✅ 自动暂停 Agent + 紧急通知用户 |
| 链上异常（如预言机操纵） | — | ✅ Guard 触发紧急暂停 |

## 三、ERC-4337、Safe、Guard/Policy 机制解析

### 3.1 它们分别是什么？

#### ERC-4337 —— 账户抽象标准

**一句话理解**：把钱包从「一个私钥控制的账户」变成「一个可以编程规则的智能合约账户」。

传统 EOA 钱包（比如 MetaMask 默认账户）的逻辑很简单：
- 谁有私钥，谁就能签名
- 必须用 ETH 付 gas
- 权限是「全有或全无」

ERC-4337 引入了一个新的交易流程：

```
传统 EOA：
  用户 → 直接签名交易 → 广播到链上

ERC-4337：
  用户/应用 → 创建 UserOperation → Bundler 收集打包
  → EntryPoint 合约 → 智能账户验证 & 执行 → Paymaster 可代付 gas
```

**为什么对 Agent 重要？**
- Agent 不需要拿用户的主私钥
- 可以给 Agent 一个「Session Key」—— 限制它只能调用某些合约、花某些金额
- Gas 可以由 Paymaster 代付，Agent 不需要持有 ETH
- 验证逻辑可以定制：多签、时间锁、额度限制都可以写进账户

#### Safe（Gnosis Safe）—— 多签智能钱包

**一句话理解**：一个需要多人（或多条件）签名才能动资产的智能钱包，就像公司的财务章需要两个经理一起盖。

Safe 是最广泛使用的多签钱包：
- 可以设定「2/3 签名」规则（3 个人里至少 2 个签名才能执行）
- 可以添加 **模块（Modules）** 扩展功能
- 可以设置 **Guard** 做额外的安全检查

**为什么对 Agent 重要？**
- Agent 可以作为 Safe 的一个「签名者」，但只有 1 票
- 大额操作需要用户的签名才能凑够门槛
- Safe 的模块机制可以给 Agent 添加 Session Key 权限
- Guard 可以在每笔交易执行前做最终检查

#### Guard / Policy —— 安全守卫

**一句话理解**：Guard 是 Safe 的「安检门」，每笔交易在执行前都必须过这一关。

Safe Guard 是一个合约，它在每笔交易执行**之前**和**之后**都会被调用：

```
交易准备执行
    ↓
🛡️ Guard.checkTransaction()  ← 在这里检查：金额、目标合约、方法...
    ↓
交易实际执行
    ↓
🛡️ Guard.checkAfterExecution()  ← 在这里检查执行后的状态是否正常
```

**Guard 能检查什么？**
- 目标合约是否在白名单
- 转账金额是否超过限额
- 调用方法是否在允许列表
- 当日累计是否超过预算
- 交易是否触发了异常状态

**Policy（策略引擎）** 是更高层的概念，定义了 Agent 的完整行为边界：
- 什么时候可以自动执行
- 什么时候需要人工确认
- 失败后怎么处理
- 日志记录什么

### 3.2 它们解决的是哪类风险？

| 风险类型 | 没有这些机制时 | 有这些机制后 |
|---------|--------------|------------|
| **私钥泄露** | Agent 拿到主私钥 = 全部资产被盗 | Agent 只有 Session Key，权限受限 |
| **权限过宽** | Agent 可以做任何事，包括转走全部资产 | Session Key 限定合约、方法、金额 |
| **不可撤销** | 一旦授权，用户无法收回 | Session Key 可过期、可主动撤销 |
| **无审计** | Agent 做了什么，用户不知道 | 日志记录每一步操作 + tx hash |
| **模型幻觉** | AI 错误地调用恶意合约 | 白名单 + Guard 拦截不在列表的操作 |
| **Prompt 注入** | 恶意内容诱导 Agent 发起危险交易 | Policy 强制检查，模型不能绕过规则 |
| **Gas 被滥用** | Agent 无限消耗 gas | 日 gas 预算 + Paymaster 限额 |
| **无紧急停止** | 发现异常后无法立即阻止 | 一键暂停模块 / 冻结 Session Key |
| **单点故障** | 一个私钥丢失就全没了 | 多签 + 社交恢复 |

### 3.3 三者如何协同工作？

```

    │
    ▼

│  ┌───────────────────────────┐  │

│  │ • 每笔交易前检查 policy     │  │
│  │ • 白名单/额度/方法验证      │  │
│  │ • 异常时触发紧急暂停        │  │
│  └───────────────────────────┘  │
│                                  │
```

**核心逻辑**：
- **ERC-4337** 提供了「可编程账户」的基础设施
- **Safe** 提供了「多签 + 模块 + Guard」的执行框架
- **Guard/Policy** 提供了「每笔交易的安全检查」规则
- 三者叠加，让 Agent 可以在**受限范围内自动执行**，而用户始终保持对资产的最终控制权

### 3.4 用生活类比理解

想象你请了一个「智能管家」（Agent）帮你管理家里的快递和账单：

- **传统 EOA** = 你把家门钥匙直接给管家。管家可以做任何事，包括搬走你家所有东西。
- **Session Key** = 你给管家一张「临时门禁卡」，只能进客厅和厨房，有效期 7 天，每天最多花 100 元。
- **Safe 多签** = 你家装了一个双锁门，需要管家和你各一把钥匙才能开保险柜。
- **Guard** = 你家装了一个安检门，每次管家带东西出门都要扫描。超重、超值、不在清单上的东西一律拦下来。
- **ERC-4337** = 整套智能家居系统，让门禁卡、双锁门、安检门能互相配合工作。
- **Policy** = 你写给管家的「管理手册」，详细规定了什么可以自动做、什么必须打电话问你、什么绝对不能做。

## 四、我的思考

### 4.1 为什么「自动化」和「安全」不是对立的

很多人觉得：要安全就别自动化，要自动化就不安全。但 ERC-4337 + Safe + Session Key 的组合告诉我们，**自动化和安全可以共存，关键在于把「权限空间」画清楚**。

Agent 不需要「全权代理」，它需要的是一个被明确定义的「行动围栏」——在围栏内自由行动，碰到围栏就必须停下来问人。这就像给小朋友一张「超市购物清单」：在这个清单内的东西可以自己拿，不在清单上的要打电话问妈妈。

### 4.2 对我（零基础学习者）的启示

理解这套机制之前，我以为「AI Agent 管钱」就是把私钥交给 AI。这太可怕了 —— 等于把银行卡密码告诉一个可能会犯错的机器人。

现在我理解了：**真正安全的设计是「给 Agent 一个有限的、可撤销的、可审计的临时权限」，而不是「把主钥匙交出去」**。这个思路不仅适用于 Web3，也适用于任何需要 AI 代理执行的场景（比如企业 RPA、自动化运维）。

### 4.3 开放问题

1. **Session Key 的粒度怎么定？** 太粗则安全风险大，太细则 Agent 几乎什么都不能自动做。有没有一个「最佳实践」的平衡点？
2. **Guard 的 gas 成本**：每笔交易都要过 Guard 检查，这会额外消耗多少 gas？在 L1 上是否划算？
3. **多 Agent 场景**：如果有多个 Agent 共用一个 Safe，它们的 Session Key 之间会不会冲突？谁优先？
